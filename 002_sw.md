# Service Worker (sw.js) - Complete Documentation

## Overview

The service worker (`sw.js`) acts as the **communication bridge** between the WebSocket server and content scripts running in web pages. It implements the message routing part of the full round-trip communication pattern, maintains WebSocket connections, manages tab state, and orchestrates page scanning.

**File:** `/Users/andy7string/Projects/Om_E_Web/web_extension/sw.js`

---

## Full Round-Trip Communication Pattern

```
1. WebSocket Server → Service Worker: Receives command via WebSocket
2. Service Worker → Content Script: Sends command via chrome.tabs.sendMessage
3. Content Script → DOM: Executes command on current page
4. Content Script → Service Worker: Sends response via sendResponse
5. Service Worker → WebSocket Server: Forwards response via WebSocket
6. WebSocket Server → Test Client: Routes response to original client
```

**Complete Message Flow:**
```
Test Client → WebSocket Server → Service Worker → Content Script → DOM
→ Response → Service Worker → Server → Test Client
```

---

## Key Responsibilities

1. **WebSocket Management** - Maintain persistent connection to server (port 17892)
2. **Message Routing** - Route commands to appropriate tabs and responses back to server
3. **Tab Lifecycle** - Handle tab creation, activation, navigation, and removal
4. **Page Version Tracking** - Manage per-domain page versions across tab navigations
5. **Scan Orchestration** - Coordinate scanning to prevent overlaps and ensure clean state
6. **Keep-Alive** - Prevent Chrome from suspending the service worker
7. **Site Config Broadcasting** - Distribute site configurations to all content scripts
8. **Cache Management** - Clear tab caches on navigation and tab switches

## Page Version Management (Chrome Storage API)

### Overview
The service worker implements **persistent page version tracking** using `chrome.storage.local` to maintain version counters across:
- Extension reloads
- Browser restarts
- Tab navigations

### Storage Structure
```javascript
{
  "version": "1.0",
  "lastUpdated": "2025-11-23T...",
  "tabs": {
    "123": {
      "domains": {
        "youtube.com": {
          "currentVersion": 5,
          "lastScanAt": "2025-11-23T..."
        },
        "google.com": {
          "currentVersion": 3,
          "lastScanAt": "2025-11-23T..."
        }
      }
    }
  }
}
```

### Business Rules
1. **Tab closes** → Delete all domains for that tab
2. **First scan on domain** → Version 1
3. **Navigation on same domain** → Increment version (1 → 2 → 3...)
4. **Different domain** → New entry at version 1
5. **Rescan (mutation, etc.)** → Keep same version

### Functions

#### `extractDomain(url)`
**Purpose:** Extract domain from URL (removes www. prefix)

**Input:**
- `url` (string): Full URL

**Output:**
- (string): Domain name (e.g., "youtube.com")
- (null): If URL parsing fails

**Example:**
```javascript
extractDomain("https://www.youtube.com/watch") → "youtube.com"
extractDomain("https://google.com/search") → "google.com"
```

**Called by:** `getPageVersion`, `setPageVersion`, `incrementPageVersion`, `resetPageVersion`, `deleteTabPageVersions`

## WebSocket Connection Management

### `connectWebSocket()`
**Purpose:** Initialize WebSocket connection to server

**Input:** None

**Output:** (Promise<void>)

**Behavior:**
1. Checks if connection already exists or is connecting
2. Creates WebSocket connection to `ws://127.0.0.1:17892`
3. Sets up event handlers:
   - `onopen`: Send bridge_status, tabs info, active tab info, flush pending messages, send heartbeat
   - `onmessage`: Forward to `handleServerMessage()`
   - `onclose`: Attempt reconnect after 1s delay
   - `onerror`: Log error

**Calls:**
- `sendToServer` - Send bridge_status message
- `sendTabsInfo` - Send initial tabs information
- `sendActiveTabInfo` - Send active tab info
- `flushPendingMessages` - Send queued messages
- `sendHeartbeat` - Send initial heartbeat

**Called by:**
- `handleSetWsUrl` - When URL changes
- `sendHeartbeat` - If connection lost
- `handleForceExtensionReload` - After clearing state
- `chrome.runtime.onStartup` listener
- `chrome.runtime.onInstalled` listener
- Initial execution at script load

---

### `sendToServer(data)`
**Purpose:** Send message to WebSocket server

**Input:**
- `data` (Object): Data to send to server

**Output:** void

**Behavior:**
- If WebSocket is open: Send immediately as JSON
- If WebSocket not ready: Queue message in `pendingMessages`

**Calls:** `ws.send()`

**Called by:** Almost all functions that need to communicate with server (40+ call sites)

---

### `flushPendingMessages()`
**Purpose:** Flush pending messages when WebSocket becomes ready

**Input:** None

**Output:** void

**Behavior:**
- Iterates through `pendingMessages` array
- Sends each message via WebSocket
- Clears the pending messages array

**Calls:** `ws.send()`

**Called by:** `connectWebSocket` (on connection open)

## Scan Orchestration

### `requestScan(tabId, url, trigger)`
**Purpose:** **UNIFIED SCAN REQUEST** - Single entry point for ALL scan triggers

**Input:**
- `tabId` (number): Tab ID to scan
- `url` (string): Current URL
- `trigger` (string): Trigger reason (e.g., "url_change", "spa_navigation", "post_action", "page_refresh")

**Output:** (Promise<void>)

**Behavior:**
1. Assigns scan request number for debugging
2. Skips chrome:// URLs
3. **DEDUPE:** Ignores if scan already in progress
4. **DEDUPE:** Skips if same URL already scanned (unless forced trigger)
5. **PAGE VERSION LOGIC:**
   - If `page_refresh`: Reset to version 1
   - If new URL: Increment version
   - If rescan: Keep existing version
6. Marks scan in progress in `tabState`
7. Injects content script if needed
8. Sends `start_scan` message to content script with pageVersion

**Forced Triggers (always rescan):**
- `post_action`
- `significant_dom_change`
- `page_refresh`

**Calls:**
- `getPageVersion`
- `resetPageVersion`
- `incrementPageVersion`
- `chrome.scripting.executeScript()`
- `chrome.tabs.sendMessage()`

**Called by:**
- `chrome.webNavigation.onCompleted` listener
- `chrome.webNavigation.onHistoryStateUpdated` listener
- `handleExecuteLLMAction` (post-action scan)
- Content script via `request_scan` message

---

```javascript
  currentFramework: 'generic',
  siteConfigError: null,
  lastConfigError: null
}
```

**Calls:**
- `clearTabCache`
- `ensureContentScriptFresh`

**Called by:** `sendTabsInfo`

## Utility Functions

### `findActiveTab()`
**Purpose:** Find the currently active tab with enhanced detection

**Input:** None

**Output:** (Promise<Object|null>)

**Behavior:**
Implements multiple strategies:

1. **Strategy 1:** Find currently active tab in current window
   - Check if accessible via `isTabAccessible`
   - Force refresh tab info

2. **Strategy 2:** Find tab in last focused window
   - Check if accessible
   - Force refresh tab info

3. **Strategy 3:** Find any accessible tab in current window
   - Filter for accessible tabs
   - Sort by priority (non-chrome URLs, then active tabs)

4. **Last Resort:** Find any visible non-chrome tab across all windows
   - Filter for accessible and visible tabs
   - Sort by priority (active tabs first)

**Calls:**
- `chrome.tabs.query()`
- `chrome.tabs.get()`
- `chrome.windows.getCurrent()`
- `isTabAccessible`

**Called by:**
- `handleNavigateCommand`
- `handleDOMCommand`
- `handleExecuteLLMAction`
- `handleExecuteCapability`
- `handleIntelligenceUpdate`
- `getCurrentActiveTabId`

## Bridge Role Summary

The service worker acts as a **bidirectional bridge** between:

### External World ↔ Service Worker
- **WebSocket Server** (port 17892)
  - Receives: Commands from test clients/LLMs
  - Sends: Responses, intelligence updates, status messages

### Service Worker ↔ Extension
- **Content Scripts** (running in web pages)
  - Receives: Intelligence updates, DOM changes, scan completions
  - Sends: Action execution commands, scan triggers, site configs

### Message Transformation
The service worker performs message normalization:
1. **Command routing:** Routes server commands to appropriate tabs
2. **Response aggregation:** Collects responses from content scripts
3. **Data enrichment:** Adds tab metadata to intelligence updates
4. **Protocol translation:** Converts between WebSocket and Chrome messaging APIs

### State Management
The service worker maintains:
1. **Page versions:** Persistent per-domain version tracking
2. **Tab state:** Active tabs, scan status, cache status
3. **Site configs:** Cached site configurations
4. **Connection status:** WebSocket health and keep-alive

## Critical Design Patterns

### 1. Scan Coordination
- **Single entry point:** `requestScan()` handles all scan triggers
- **Deduplication:** Prevents overlapping scans on same tab
- **Version tracking:** Maintains page version across navigations
- **Forced triggers:** Certain triggers bypass deduplication

### 2. Keep-Alive Strategy
- **Multiple mechanisms:**
  - Keep-alive ports from accessible tabs
  - Offscreen document as fallback
  - Periodic heartbeat alarms
  - Connection health monitoring

### 3. Message Queueing
- **Pending messages:** Queue messages when WebSocket not ready
- **Flush on connect:** Send queued messages when connection established

### 4. Tab State Tracking
- **In-memory state:** Fast access for active operations
- **Persistent storage:** Survives extension reloads
- **Enhanced metadata:** DOM changes, site config status, network activity

### 5. Action Coordination
- **Action in progress flag:** Prevents content script refresh during action execution
- **Post-action scan:** Triggers rescan after action completes
- **Error recovery:** Clears flag on failure/exception

---

## Performance Considerations

### 1. Storage Access
- **Async operations:** All storage access is async
- **Minimal writes:** Only write when state changes
- **Batch updates:** Update multiple fields in single write

### 2. Tab Queries
- **Cached state:** Use `internalTabState` for quick lookups
- **Force refresh:** Use `chrome.tabs.get()` for critical operations

### 3. Content Script Injection
- **On-demand:** Only inject when needed
- **Error handling:** Gracefully handle injection failures
- **Reinjection prevention:** Check if already fresh before reinjecting

### 4. WebSocket Health
- **Auto-reconnect:** Reconnect on disconnection
- **Heartbeat:** Keep connection alive with periodic pings
- **Pending queue:** Don't lose messages during disconnection

## Error Handling Patterns

### 1. Try-Catch Blocks
All async functions wrap operations in try-catch:
```javascript
try {
  // Operation
  sendResponse({ ok: true, result });
} catch (error) {
  console.error("[SW] Error:", error);
  sendResponse({ ok: false, error: error.message });
}
```

### 2. Tab Access Validation
Check if tab is accessible before operations:
```javascript
if (!isTabAccessible(tab)) {
  console.log("[SW] Tab not accessible");
  return;
}
```

### 3. WebSocket State Checks
Verify WebSocket is open before sending:
```javascript
if (ws && ws.readyState === WebSocket.OPEN) {
  ws.send(JSON.stringify(data));
} else {
  pendingMessages.push(data);
}
```

### 4. Content Script Communication
Handle content script absence gracefully:
```javascript
try {
  await chrome.scripting.executeScript({...});
} catch (injectError) {
  console.log("[SW] Injection failed:", injectError.message);
}
```

## Conclusion

The service worker (`sw.js`) is the **central communication hub** of the Om_E_Web extension. It:

1. **Bridges** external clients (via WebSocket) with content scripts (via Chrome messaging)
2. **Orchestrates** page scanning to ensure clean, non-overlapping scans with version tracking
3. **Manages** tab lifecycle, state tracking, and cache management
4. **Maintains** persistent connections using keep-alive mechanisms
5. **Routes** messages bidirectionally between server and content scripts
6. **Transforms** messages between WebSocket and Chrome messaging protocols

This architecture enables **programmatic web automation** where LLMs can interact with web pages through a clean, versioned, action-based interface without manual interaction or complex scripting.
