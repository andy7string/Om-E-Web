# Service Worker (sw.js) - Function Documentation

## Overview

The service worker (`sw.js`) acts as a **communication bridge** between the WebSocket server (Python) and content scripts running in browser tabs. It orchestrates the full round-trip communication pattern for LLM-driven web automation, managing tab state, WebSocket connections, and message routing across all components of the Om_E_Web system.

**Core Responsibilities:**
- Maintain persistent WebSocket connection to Python server (port 17892)
- Route commands between server and content scripts
- Manage tab lifecycle (creation, activation, navigation, removal)
- Track page versions and scan state per tab
- Coordinate intelligence scanning and artifact generation
- Handle capability execution and LLM actions
- Implement keep-alive mechanisms to prevent service worker suspension
- Manage site configuration distribution and caching

## Architecture

### Communication Flow
```
Test Client → WebSocket Server → Service Worker → Content Script → DOM
                                        ↓
                                  Tab Management
                                        ↓
                              State Tracking (Chrome Storage)
```

### Key Data Structures

**In-Memory State:**
- `ws`: WebSocket connection to server
- `tabState`: Map of tab scan states (scanInProgress, lastUrl)
- `internalTabState`: Enhanced tab metadata (DOM changes, site config, network activity)
- `tabCache`: Cached tab data for performance
- `siteConfigs`: Local copy of site configurations
- `keepAlivePorts`: Set of active keep-alive ports
- `pendingMessages`: Queue for messages when WebSocket is unavailable

**Persistent State (Chrome Storage):**
- `tabState`: Per-domain page versioning (survives reloads)

**Purpose:** **UNIFIED SCAN REQUEST** - Single entry point for all scan triggers
**Parameters:**

6. Release lock on error

## Critical Patterns & Best Practices

### Action In Progress Protection
The `actionInProgress` flag (not shown as a declared variable but used throughout) prevents critical operations during action execution:
- Blocks content script refresh (line 666)
- Blocks automatic DOM mutation rescans (line 1467)
- Blocks network idle rescans (line 1544)

**Pattern:**
```javascript
if (actionInProgress) {
  console.log("[SW] ⏸️ Skipping X - action in progress");
  return;
}
```

### Scan Deduplication
`requestScan()` implements multiple deduplication strategies:
1. **Lock-based**: Check `scanInProgress` flag
2. **URL-based**: Skip if same URL already scanned (unless forced)
3. **Forced triggers**: Specific triggers bypass URL check (post_action, significant_dom_change, page_refresh, tab_switch)

### Error Handling Pattern
All message handlers follow consistent error handling:
```javascript
try {
  // ... operation
  sendResponse({ ok: true, result: ... });
} catch (error) {
  console.error("[SW] ❌ Error:", error);
  sendResponse({ ok: false, error: error.message });
}
```

### Async Response Handling
Message listeners that perform async operations return `true` to keep response channel open:
```javascript
chrome.runtime.onMessage.addListener((message, sender, sendResponse) => {
  // ... async operations
  return true; // Keep channel open
});
```

### Tab Accessibility Checks
Always check `isTabAccessible()` before attempting content script injection to avoid permission errors on chrome://, extension://, and about: pages.

## Performance Considerations

### Keep-Alive Strategy
- **Offscreen document**: Preferred method (always available)
- **Tab injection**: Fallback when no HTTP(S) tabs available
- **Periodic check**: Every 30 seconds verify port exists
- **Alarm-based**: 1-minute heartbeat prevents suspension

### Message Queuing
- Pending messages queued when WebSocket unavailable
- Flushed on connection open
- Prevents message loss during reconnection

### State Management
- **In-memory**: Fast access for scan locks, tab state
- **Chrome Storage**: Persistent across reloads for page versions
- **Hybrid approach**: Balance between speed and persistence

### WebSocket Reconnection
- Automatic reconnect with 1-second delay
- Preserves pending messages
- Re-establishes bridge status and sends tab info

## Architecture Notes

### MV3 Service Worker Lifecycle
- Service workers are **event-driven** and can be suspended by Chrome
- Keep-alive mechanisms prevent suspension:
  - Long-lived port connections
  - Periodic alarms
  - Offscreen documents
- WebSocket connection must survive worker suspension

### Message Flow Complexity
- **3 layers:** Test Client ↔ Server ↔ Service Worker ↔ Content Script
- **Bidirectional:** Requests and responses flow both directions
- **Async:** All operations are promise-based
- **Stateful:** Tracks tab state, scan locks, pending messages

### State Synchronization Challenges
- **Tabs can change rapidly:** Navigation, creation, removal
- **Content scripts can disappear:** Page refresh, CSP restrictions
- **WebSocket can disconnect:** Network issues, server restart
- **Service worker can suspend:** MV3 lifecycle management

The architecture handles these challenges through:
- Persistent storage for critical state
- Message queuing for transient disconnections
- Keep-alive mechanisms for service worker persistence
- Robust tab discovery with fallback strategies
