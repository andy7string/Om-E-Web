## CRITICAL BUG IDENTIFIED

### Bug Summary

**"Actionable element not found"** errors occur because the content script's `actionableElements` Map is cleared at the start of every scan but never repopulated after extraction completes.

### Root Cause

**File:** `/Users/andy7string/Projects/Om_E_Web/web_extension/content.js`
**Function:** `IntelligenceEngine.prototype.extractSemanticTextWithIds()` (line 6233)

**The Flow (BROKEN):**

1. **Line 6255:** `this.actionableElements.clear()` - Map is emptied
2. **Lines 6445-6668:** DOM tree walk generates action IDs and actionables array
3. **Line 6572:** `data-ome-action-id` attributes written to DOM
4. **Line 6575-6582:** Actionables array built: `[{id, type, label, tag, href, selector}, ...]`
5. **Line 6664-6668:** Function returns `{text, actionables}` to caller
6. **Line 7094:** `semanticPageData: this.extractSemanticTextWithIds()` sent to server
7. **❌ BUG:** Map is NEVER repopulated after function returns

**When execute_action arrives:**

8. **Line 11329:** execute_action listener receives message
9. **Line 11362:** `intelligenceEngine.getActionableElement(actionId)` called
10. **❌ FAILURE:** Returns null because Map is empty

### Why This Matters

- Server has ELEMENT_REGISTRY populated (from actionables array)
- DOM has data-ome-action-id attributes (written during scan)
- text.md has action IDs (generated from text string)
- But content script has NO way to resolve action ID → DOM element

## THE FIX

### Option A: Quick Fix (Immediate)

**File:** `/Users/andy7string/Projects/Om_E_Web/web_extension/content.js`
**Location:** After line 7094 (after semanticPageData assignment)

**Add this code:**

```javascript
// 🔧 CRITICAL FIX: Repopulate actionableElements Map after extraction
// The extractSemanticTextWithIds() function clears the Map but never repopulates it.
// We need to rebuild the Map from the actionables array for executeAction to work.
if (semanticData && semanticData.actionables) {
    intelligenceEngine.actionableElements.clear();

    for (const actionable of semanticData.actionables) {
        // Query DOM using data-ome-action-id attribute (written during extraction)
        const element = document.querySelector(`[data-ome-action-id="${actionable.id}"]`);

        if (element) {
            // Store both the DOM reference AND metadata
            intelligenceEngine.actionableElements.set(actionable.id, {
                element: element,  // DOM reference for execution
                ...actionable      // Metadata: {id, type, label, tag, href, selector}
            });
        } else {
            console.warn(`[Content] ⚠️ Failed to find element for ${actionable.id}`);
        }
    }

    console.log(`[Content] ✅ Repopulated actionableElements Map: ${intelligenceEngine.actionableElements.size} elements`);
}
```

**Impact:**
- ✅ Fixes immediate bug
- ✅ Minimal code change (~15 lines)
- ✅ No server changes required
- ✅ No breaking changes
- ⚠️ Still vulnerable to DOM re-renders (attributes can be lost)
- ⚠️ Still vulnerable to content script reinjection

**Testing:**

## CONCLUSION

The Om_E_Web system has a **critical but simple bug** that prevents LLM actions from executing.
The bug is in the content script's element ID management - the Map is cleared but never repopulated.

**The immediate fix is straightforward** (~15 lines of code) and will unblock LLM functionality today.

**The long-term solution** (selector-based lookup) is well-designed and follows the capability
pipeline pattern. It's more robust and future-proof, but requires careful incremental rollout.

**Both approaches should be implemented:**
1. Quick fix NOW to unblock users
2. Long-term solution over next 2 weeks
3. Remove quick fix once long-term solution is proven stable

The selectorslookup.md implementation plan is **comprehensive and ready for execution**.
